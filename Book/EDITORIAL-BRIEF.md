# Editorial brief

Write for a developer who can run a repository's tests and uses a coding agent. Explain the task before the protocol or report field.

## Voice

- Lead with the action or problem. Use concrete subjects and active verbs.
- Keep paragraphs short. Delete repeated introductions, takeaways, and promises to explain something later.
- Prefer one useful example to a long catalogue.
- Define a term once, then use it consistently.
- Keep exact tool names and fields where readers need them. Explain their purpose in plain language.
- Use finding titles first; explain the clone-type tags readers actually see.
- Do not pad chapters to word or page quotas.

## Evidence

A match establishes a relationship between source ranges. It does not choose ownership or prove that extraction preserves behavior. Rank measures impact, not confidence.

Use actual product captures for UI. Diagrams explain workflows. Never fabricate scores, commands, source output, or cleanup results. Record binary hashes and screenshot provenance. Mark exercises as exercises and use the reader's own code unless a runnable fixture is supplied.

## Workflow

Check proposed code with `find-similar`; inspect `clusters` and `existing`. For cleanup, start with `duplicates`, inspect a chosen group, record the baseline, change one group, and verify behavior and remaining occurrences. Keep deliberate duplication for a stated technical reason.

Correct stale claims against the installed tools, implementation, and specifications. Omit unresolved claims. The current edition is a concise draft, not a claim that every workflow has been captured end to end.
