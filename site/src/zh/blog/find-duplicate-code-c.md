在一个 C 文件中修好了漏洞，另一个文件里可能还留着同样的问题。假设两个函数都要打开文件、分配缓冲区并读取数据。你给第一个函数的读取不足分支补上了 `fclose`，另一个函数却仍会泄漏文件句柄。

Deslop 现在可以在 `.c` 和 `.h` 文件中查找重复代码。它能找到重复的函数以及更小的代码块，即使有人重命名了变量或修改了常量。

## 为什么重复代码在 C 语言中风险更高

在大多数语言中，复制的函数只是一笔维护成本；在 C 中，它往往是一个正确性风险。C 没有析构函数，没有 `defer`，也没有垃圾回收器，因此每个获取资源的函数都必须在每条退出路径上手动释放它。错误处理代码块冗长、重复，而且很容易被复制。它们也是漏洞藏身之处，因为失败分支在测试中运行的次数最少。

当同一段“打开、分配、读取、清理”的流程存在于多个地方时，对这段流程的每一次修复都必须落实到每一处：

- 提前返回时遗漏了 `free`；
- 部分读取后执行了两次 `fclose`；
- 长度检查本该用 `<=` 却用了 `<`；
- 一个调用方检查了返回码，另一个却忽略了它。

静态分析工具和消毒器可以在这些问题发生时捕获其中一部分。重复代码检测器回答的是另一个问题：*这段代码还存在于哪里？*修好一个漏洞之后，正是这个问题决定了修复是否完整。

## 在 VS Code 中查找复制的 C 错误处理

在一个包含两个文件的示例中，音频加载器和数据帧读取器都会分配缓冲区，再从文件中读取数据。Deslop 找到了这两个文件中相似的错误处理。打开数据帧读取器后，还可以看到另一处值得检查的重复。读取不足的分支和正常关闭函数都会释放缓冲区、关闭文件，再释放外层包装结构体。

下面这种代码块往往会被重复：

```c
if (fread(buf->data, 1, size, fp) != size) {
    free(buf->data);
    fclose(fp);
    free(buf);
    return NULL;
}
```

在 VS Code 中对照两条路径，检查每条路径各自拥有哪些资源。如果适合提取共享的清理函数，请保留每个调用方原有的日志和返回值。除了正常读取，也要测试读取不足的路径，然后再次扫描。

集群面板会列出每个副本及其文件和行号范围。**Compare To Canonical** 会打开与参考副本并排对比的视图，而 **Select for Compare** 加上随后的 **Compare with Selected** 则让你自行选择任意两个副本进行对比。[集群面板指南](/zh/docs/vscode-cluster-panel/)详细介绍了每一步操作。

## Deslop 将哪些 C 代码视为相同

Deslop 使用 tree-sitter 的 C 语法解析每个文件，比较的是规范化后的语法树，而不是文本行。在 C 语言中，这意味着：

- **改名不会掩盖复制。**函数名、结构体成员、typedef、`goto` 标签和变量名都会被规范化，因此 `read_frame` 和 `load_audio` 仍然可以匹配。
- **类型替换不会掩盖复制。**在复制的函数中把 `int` 改成 `long`，其结构保持不变。
- **常量改动不会掩盖复制。**数字、字符和字符串都会被规范化，因此缓冲区大小或错误信息不同的副本仍然会匹配。
- **注释和格式会被忽略。**注释不会进入 C 语法树，空白字符和大括号风格也从不参与比较。

结构匹配只会让一对代码成为候选。随后 Deslop 会检查源码内容：一致的重命名仍算复制，但调用了不同的函数或执行了不同的操作，就是不同的代码。两个看起来相似但做的事不同的循环会被报告为 **Same shape, different content**，这类信息仅供参考，不计入重复率数据。

## 扫描会报告什么

重复的头文件引用、函数声明和普通循环头在 C 中很常见。Deslop 不会仅凭这些内容报告重复，也不会比较宏定义体。如果生成的文件占据了报告的大部分，可以[配置报告显示哪些结果](/zh/docs/configuration/)。

更具体地说：

- **`#include` 和 `#define` 行属于脚手架代码。**它们绝不会成为克隆的证据。`#ifdef` 等条件块包含真实代码，仍会比较。
- **函数原型不是克隆。**名称一经规范化，每个短原型的形状都相同，因此一个列出三个互不相关函数的头文件本来会与任何其他头文件匹配。函数*主体*才是证据。只由包含保护（include guard）和原型构成的头文件不会报告任何内容。
- **函数指针表会被比较。**像 `int (*on_open)(const char *, int);` 这样的声明是一个变量而非原型，因此被复制的钩子表会像其他被复制的代码一样被报告。
- **宏体不会被展开。**C 语法把 `#define` 的主体保存为一个不透明的 token，因此两个被复制的宏是已知的盲点，而不是错误匹配的来源。
- **尚不支持 C++。**`.h` 文件会按 C 分析。

这些规则把 C 语言中的常见噪音挡在报告之外，让剩下的集群都是你真正可以着手处理的复制代码。

## 扫描你的 C 项目

[安装 Deslop](/zh/docs/)，然后在项目根目录运行：

```bash
deslop .
```

打开 HTML 报告，或者通过 VS Code 扩展跳转到各处副本。先看排名最高的结果，判断这些副本是否应该应用同样的修复。

结果按[重复质量](/zh/blog/ranking-formula/)排序：被复制的语法树的大小乘以它的额外副本数。一个出现四次的较长错误处理代码块，排名会高于一个出现两次的短小辅助函数。

## 防止新的重复代码混入

现有的重复代码分诊完毕后，更省力的做法是在新的副本合入之前就发现它们。以下两种方式很适合 C 项目：

- **CI 门禁。**[GitHub Action](/zh/docs/github-action/) 会在拉取请求中运行同一个 CLI。设置[重复率阈值](/zh/docs/configuration/#threshold--ci-)，在重复率上升时让任务失败；也可以只测量不设门禁，同时逐步清理。
- **编码代理检查。**如果你在 C 代码库上使用 Claude Code、Codex 或其他 MCP 客户端，可以让代理在编写新的清理路径之前先调用 Deslop 的 `find-similar` 工具。如果已存在匹配的函数，代理可以直接调用它，而不是再添加一个副本。[AI Agents](/zh/docs/ai-integration/) 介绍了具体设置。

一旦知道所有副本的位置，修复被复制的清理路径就很容易了。
