C 支持采用与 Deslop 其他语言相同的结构化流水线：用 tree-sitter 解析而非正则表达式、归一化标识符和字面量而非匹配原始代码行、将最严重的重复排在最前面，并在代码变化时提供实时 LSP 和 MCP 反馈。`.c` 和 `.h` 文件会被发现、用 [`tree-sitter-c`](https://github.com/tree-sitter/tree-sitter-c) 解析，然后送入[工作原理](/zh/docs/how-it-works/)中记录的共享指纹、同级节点窗口、词元和排名阶段。

## 为什么是 C，为什么是现在

[Osprey](/zh/docs/osprey/) 编译器附带一个手写的 C 运行时：约 190 个文件、46,000 行代码，以警告即错误的方式编译。它的维护者希望这个运行时也能享有他们在 Osprey 和 Python 源码上已有的同一道重复检查关卡，并点名了他们最在意的形状：被复制的错误路径和清理块。一个加载器打开文件、分配缓冲区、读取内容，每一步都有一级 `if (x == NULL) { fprintf(...); free(...); return NULL; }` 阶梯。下一个加载器靠复制第一个写成。后来其中之一得到了修复。

对该运行时的首次扫描测得 7.5% 的重复率，其中大部分是重复的测试准备代码，同时它也测出了两个误报，如今已由测试夹具钉死。下文会描述这两者，因为检测器拒绝报告什么，与它发现了什么同样重要。

## C 解析器能看到什么

归一化后的语法树保留结构、丢弃拼写：

- `identifier`、`field_identifier`、`type_identifier`、`statement_identifier` 和 `primitive_type` 坍缩为统一标记，因此重命名函数、结构体成员或 typedef，或者把 `int` 换成 `long`，都不会藏住副本；
- 数字、字符、字符串内容、转义序列、`<system.h>` 路径、`true`、`false` 和 `NULL` 坍缩为统一的字面量标记，而字符串和字符的外壳保持结构性，使拼接的字符串保有各自的形状；
- 注释消失；
- 指针、数组和函数声明符、强制转换、`sizeof`、复合字面量、初始化列表、指派符、存储类、类型限定符以及每一种语句形式都保持结构性。

一个每个局部变量都被重命名、缓冲区大小也被改动的被复制函数，仍然是同一棵语法树。

## C 解析器拒绝统计什么

**宏。** 语法分析永远看不到宏展开成什么。`#define` 的体是一个不透明的叶子节点，因此两个毫不相关的宏会生成相同的指纹。于是 `#include`、`#define` 和类函数宏定义都被视为脚手架，就像 C# 里的 `using` 或 Python 里的 `import`：永远不是克隆证据，也永远不会自成聚簇。六个文件只共享相同的 include 块和常量、别无其他，则不会报告任何聚簇。重复的宏体是一个有据可查的漏报，而不是被容忍的误报。

**原型。** 归一化之后，每个单参数原型都是同一个形状。否则，声明了 `sqrt`、`exp` 和 `log` 的头文件会与任何声明三个不相关函数的头文件匹配，而 Osprey 的 `math.h` 垫片恰恰这样命中过一个不相干的测试头文件。原型是对住在别处的函数体做出的承诺；函数体才是证据。一个由 include 守卫和原型构成的头文件不会报告任何内容。

**循环头。** 在 C 中，`for` 的初始化、条件和更新紧挨着循环体，因此一段相邻节点可能只是一句 `for (int i = 0; i < n; i++)`。那是每个循环都有的惯用法，不是副本。对于以这种方式排布 `for` 头的任何语言，Deslop 都不再在扁平的 `for` 头上形成同级节点窗口。

## 它会报告什么

为 Osprey 的需求编写的测试夹具在两个文件中放了两个加载器。每个都打开句柄、分配、读取，并用一级被复制的“记录日志、释放、返回”阶梯检查每一步。Deslop 将两个文件共享的阶梯报告为 **Similar code**，并在其中一个文件内把短读错误路径与按相同顺序释放相同资源的析构函数报告为 **Identical code**。这正是审查者想要的两个发现：会在文件之间各自漂移的副本，以及理应成为一个函数的清理序列。

## 查找重复的 C 函数与复制粘贴块

从整个仓库开始，这样分处不同 `.c` 和 `.h` 文件的匹配块才能被比较。既审查完全相同的函数，也审查重命名了变量或更改了常数的近似重复。一个有用的匹配可以是较大函数内部重复出现的块，比如两个加载器共享的错误处理。

对每个发现，把各处出现并排比较。在抽取共享函数之前，检查返回值、资源所有权、指针生命周期和副作用。结构相似是审查代码的理由。决定共享什么还需要理解其行为。

## 安全地重构重复的清理代码

清理辅助函数应当让所有权显式化。弄清每个分配或文件句柄归哪个函数所有，以及哪些失败路径已经释放了它。把辅助函数需要的资源传给它，并保持清理操作的顺序。合并两条被复制的错误路径时，必须保留每个调用者的错误码和日志行为。

抽取完成后，运行项目的测试并再次扫描。审查剩余聚簇中第一次重构暴露出的更小的重复块。把这个循环保持得很小，就能更容易发现被改动的失败路径或被释放两次的资源。

## 预防胜过清理冲刺

Deslop 的 MCP 服务器为编码智能体提供由实时工作区支撑的 `find-similar` 工具。在智能体编写另一个加载器、另一条错误阶梯或另一个测试夹具之前，它可以提交拟议的代码形状，并询问仓库中是否已经存在。强匹配会让任务从“编写新的实现”变成“复用或扩展规范实现”。MCP 配置请参阅 [AI 集成](/zh/docs/ai-integration/)，智能体工作流则见[面向 AI](/zh/docs/for-ai/)。

## 生成的 C 代码

在许多仓库中，生成的解析器是最大的 C 文件，而 tree-sitter 解析器生成器不会写入“generated”横幅，因此 Deslop 像分析其他源码一样分析它们。Osprey 自己生成的解析器有 86,500 行、29% 自相似，仅它一项就足以击穿仓库关卡。正确的答案是对该目录使用 [`report_hide`](/zh/docs/configuration/)，而不是 `exclude`：生成的代码仍留在分析中，因此与其重复的手写文件仍会被报告，而生成文件自身的重复则不会计入头条数字。

## 在 C 仓库上试试

按照[入门指南](/zh/docs/)安装 Deslop，打开一个 C 工作区，然后运行：

```bash
deslop .
```

CLI 会输出 JSON、文本和 HTML 报告。VS Code 扩展会添加实时发现结果，以及按最严重者优先排列的簇视图。从第一个簇开始：它是实测影响最大的重复，而不仅仅是扫描器碰巧先遇到的那个。
