Deslop 使用 tree-sitter 解析源文件，并比较归一化后的语法树。解析器为检测器提供稳定的结构化输入，无需依赖针对源代码文本的正则表达式。

这一个设计决策塑造了下游的一切：什么算作一份拷贝、哪些改动会隐藏拷贝、报告的位置有多精确，以及在你输入时代码报告能多快刷新。本文解释这个决策、它带来的收益，以及它的局限所在。

## 原始文本匹配会漏掉什么

原始文本匹配容易受不改变程序结构的改动影响：

- **格式。** 两个完全相同但格式不同的函数看起来像是不同的代码。
- **重命名。** 在一个方法中把 `user` 改成 `customer` 会破坏每一次匹配。
- **位置。** 一个被拷贝的函数移动到另一个文件，或同一文件中更靠下的位置，就不再位于行窗口比较所期望的行上。
- **换行。** 一个拆成三行的长参数列表，再也无法与单行的原始版本对齐。

以上每一种都是表面性的改动。它们都不会改变代码的行为，也不会让这份拷贝的维护问题减轻分毫。漏掉它们的检测器，漏掉的正是人们实际留下的拷贝：那些被粘贴、被格式化工具整理、又被重新命名以适应新位置的代码。

正则表达式让情况变得更糟而不是更好。一个试图通过文本识别函数的模式，必须猜测函数在哪里结束、哪些大括号位于字符串里、哪些 token 是注释。每一个猜测都是一个缺口：真正的重复可能从中漏过，或者两段毫不相关的代码块被粘在一起。Deslop 把这视为一个准确性问题，而不是调参问题，因此它完全不使用文本模式来处理源代码。

## tree-sitter 是什么

[Tree-sitter](https://tree-sitter.github.io/tree-sitter/) 是一个开源的解析器生成器和增量解析库。每种受支持的语言都有一个语法（grammar），可以为源文件生成一棵具体语法树。该项目自己的文档称，它快到可以在每次按键时解析，也健壮到即使文件包含语法错误也能返回可用的语法树。GitHub 在其代码导航中[使用 tree-sitter](https://docs.github.com/en/repositories/working-with-files/using-files/navigating-code-on-github)。

对一个重复代码检测器来说，有三个属性至关重要：

1. **每个文件一棵树，且带有精确位置。** 每个节点都知道自己的字节范围，因此一个发现可以指向每份拷贝的精确起点和终点。
2. **所有地方使用同一个解析器。** CLI、VS Code 扩展和 MCP 服务器都在相同的语法上运行同一个 Rust 引擎，因此拉取请求中的发现与你编辑器中的发现是一致的。
3. **容错性。** 写到一半的代码仍然可以解析成一棵树，这对于开发者或 AI 编程代理编辑到一半时的实时分析非常重要。

## tree-sitter 让我们能做什么

tree-sitter 解析器为仓库中的每个文件生成一棵 AST。从这棵树出发，我们可以：

- 将标识符和字面量归一化为规范的占位符，使重命名坍缩到同一个指纹；
- 独立地哈希子树，使一个方法的指纹无论它位于文件中的何处都保持稳定；
- 在子树而非行上进行操作，使格式和空白字符变得无关紧要；
- 返回当前源代码快照中每个出现位置的精确字节范围。

不同语言的语法会以不同方式表示标识符、字面量与样板结构，因此归一化规则按语言实现。归一化后的语法树再进入共享的指纹、聚簇与排名流水线。

目前这涵盖了 C、C#、Rust、Python、Dart、JavaScript、TypeScript/TSX、PHP、F#、Go 和 Osprey。新增一门语言意味着添加它的语法和它的归一化规则；流水线的其余部分是共享的。

## 一个小例子

下面是两个相隔数周编写的 Python 函数：

```python
def total_for_user(user, orders):
    total = 0
    for order in orders:
        if order.owner == user.id:
            total += order.amount
    return total
```

```python
def sum_customer_spend(customer, purchases):
    spend = 0
    for purchase in purchases:
        if purchase.owner == customer.id:
            spend += purchase.amount
    return spend
```

一个基于行的 diff 会看到六行不同的代码。归一化之后，两个函数拥有相同的形状：一个带有两个参数的函数、一个被初始化为字面量的累加器、一个循环、一次比较和一次加法。它们的结构指纹是匹配的。

仅凭结构匹配只能让这一对成为候选。Deslop 接着会检查源代码内容。在这个例子中，名称的变化是一致的（`user` → `customer`、`orders` → `purchases`），而且两个函数做的是同一件事，因此这样的一对一旦超过下文描述的最小规模，就会被报告为 **Nearly identical code**。如果第二个函数是做乘法而不是加法，或者在其协作者对象上调用了不同的方法，两棵树看起来可能仍然相似，但内容检查会看到不同的操作，从而拒绝将这一对视为克隆。结构负责找出候选；内容决定 Deslop 报告什么。

## 为什么归一化需要第二次检查

过度归一化是结构化检测器产生误报的方式。如果每个标识符、字面量和运算符都坍缩为占位符，许多毫不相关的函数就会开始看起来一样：每个带累加器的短循环、每个 getter、每个卫语句。

Deslop 用两种方式处理这个问题。第一，小型的子树永远不会成为克隆候选：默认最小值是 30 个语法树节点，可以通过 `--min-nodes` 配置。第二，布局匹配但几乎没有共享内容的候选会被标记为 **Same shape, different content**。这个标签仅用于提供信息。它不会增加克隆计数、重复规模或重复百分比，因此重复出现的控制流骨架不会虚增你的技术债数据。[类别指南](/zh/docs/how-it-works/#-2)列出了每一个标签。

## 这对你意味着什么

- **重命名重构不会隐藏重复。** 一个簇能在标识符重命名后存活，因为指纹是在归一化后的 AST 上计算的。
- **格式变更不会改变结构指纹。** 使用 `rustfmt` 重新格式化文件，不会改变 Deslop 所比较的语法结构。
- **位置是精确的。** 每个出现位置都是当前文件中的一个字节范围，因此 VS Code 面板、HTML 报告和 AI 代理的工具调用都指向同一处代码。
- **移动代码不会隐藏它。** 子树指纹不依赖于代码所在的位置，因此被移动到另一个文件或另一个类中的拷贝仍然会被匹配。

## tree-sitter 的能力边界

解析器只能描述文件里有什么。在 C 语言中，语法不会展开宏：`#define` 的主体是一个不透明的叶子节点。因此 Deslop 不比较宏的主体，被拷贝的宏是一个已知的漏报，而不是误报的来源。生成代码会像其他任何文件一样被解析。Deslop 默认隐藏常见的生成文件模式和横幅，你也可以[配置更多](/zh/docs/configuration/)。

用不同语法写出的等价行为，例如循环与 `map` 调用，可能根本不共享同一种树形状。可选的嵌入功能可以将这类代码作为 **Same behavior, different code** 候选呈现出来。这个标签是在请你审查两个版本；它并不能证明二者可以互换。

## 结构优先，服务于干净的代码审查

被拷贝的代码是一种[代码坏味道](https://martinfowler.com/bliki/CodeSmell.html)，而不是自动成立的 bug。解析为审查提供了坚实的起点：同一段逻辑，无论名称和格式如何都能被找到，附带精确的位置和清晰的类别。接下来的决定权在于你：提取、复用，或者有意保留这些拷贝。[工作原理](/zh/docs/how-it-works/)涵盖了完整的流水线，[研究背景](/zh/docs/research-background/)列出了每个阶段背后的论文。
