### ✅ Done

- **One output directory + incremental on by default** ([pipeline.md §OUTPUT-DIR](../specs/pipeline.md#output-dir), [§PIPELINE-INCREMENTAL](../specs/pipeline.md#pipeline-incremental), [cli.md §CLI-ARG-NO-INCREMENTAL](../specs/cli.md#cli-arg-no-incremental)): everything Deslop writes for a workspace now lands under a single `.deslop/` directory at the **scan root** — reports, `logs/`, and the former `.deslop-cache/` as `.deslop/cache/` — resolved through one new `deslop-core::paths` module that the CLI, LSP, and MCP all share instead of joining path literals of their own. The CLI's default output moved from the working directory to the scan root, so `deslop /other/repo` no longer litters wherever the operator was standing, and one `.deslop/` line replaces the three bandaid `.gitignore` patterns (the VSIX consent prompt writes that line too). Separately, the CLI's fingerprint cache flipped from opt-in `--incremental` to **on by default** with a `--no-incremental` opt-out, matching the LSP (which always ran incrementally) and the `deslop-core` invariant that batch runs are "incremental starting from an empty cache". Safe because invalidation is *addressing*, not bookkeeping ([§PIPELINE-INCREMENTAL-INVALIDATION](../specs/pipeline.md#pipeline-incremental-invalidation)): the blob filename is `blake3(contents)`, corpus membership always comes from a fresh discovery walk, and a wiped cache changes only the `cache_stats` counters. E2E proof in `crates/deslop/tests/cli/cache_and_debug.rs` (`offline_edit_invalidates_only_the_changed_file`: warm run all-hits → edit with nothing watching → exactly the edited file misses → wiped cache re-parses everything and yields the same clusters) and `crates/deslop/tests/cli/config.rs` (`default_output_written_to_deslop_dir_under_scan_root`). Because the cache always lands in the scan root and `--output` cannot redirect it, tests that scan a shared repo fixture go through a `fixture_command` helper that passes `--no-incremental`, so running the suite never writes into a checked-in fixture.
- **JetBrains: single LSP4IJ artifact + Android Studio support + report tool window** ([jetbrains.md](../specs/jetbrains.md)): dropped the native-LSP `deslop-ultimate` artifact entirely (module, Gradle includes, Makefile, `release.yml`, `ci.yml`, package-verify script, README, spec) — one LSP4IJ build now serves every IDE family. Lowered the compile base to IntelliJ IDEA Community 2024.3 and `since-build` from 261 → **243**, so the plugin actually loads on shipping Android Studio (the 261/IDEA-2026.1 floor excluded every released Android Studio — the "I don't see anything" cause). Added the **Deslop** tool window hosting the engine HTML report in a JCEF browser behind a shared `DeslopReportRenderer` project-service seam (one render path for the Tools action and the tool window Refresh; collapsed the now-single-variant action). `DeslopPluginDescriptorTest` pins the tool window / service / action / LSP4IJ server registrations so the visible surfaces can't silently vanish; the 2024.3 platform's JUnit5 launcher listener needed JUnit4 added to the test runtime. **This is not full VSIX parity** — see the gap matrix in [JetBrains native UX](jetbrains-ux-plan.md).
- **Windows MCP: cross-platform IPC transport** ([live.md §LIVE-IPC-TCP](../specs/live.md#live-ipc-tcp), [§MCP-IPC-DISCOVERY](../specs/live.md#mcp-ipc-discovery)): the MCP⇄LSP bridge no longer requires Unix domain sockets. `deslop_core::live::transport` carries the same line-delimited JSON-RPC over either a Unix socket (default on Unix, byte-for-byte unchanged) or TCP loopback (default on Windows, opt-in via `deslop-lsp --ipc-transport tcp`), discovered through the `IpcEndpointFile` record (`.deslop/cache/deslop.port`, typeDiagram model) and gated by a per-session token line. The MCP client and its `report/subscribe` reader are transport-generic; `LspNotRunning` errors name both candidate endpoints. E2E proof in `crates/deslop-mcp/tests/tcp_transport.rs` (full tool chain over TCP, token rejection, stale-record handling) — platform-neutral on purpose, and a new `windows` CI job runs `cargo check --workspace` plus that suite on `windows-latest` so `cfg(windows)` regressions can no longer ride to release unseen.
